# Requirements Document

## Introduction

Phase 10 implements the post-interview performance evaluation engine for the Candidate AI Interview Practice Portal. After a voice interview session ends and the agent handoff webhook (Phase 9) transitions the session to `interview_processing`, this pipeline executes asynchronously via FastAPI's native `BackgroundTasks`. It feeds the session transcript, parsed resume, and job description to a high-tier LLM, computes a completion-weighted score across four evaluation dimensions, maps the score to a practice verdict, generates targeted technical probe questions, and persists the full assessment to the database — advancing the session to `completed`.

## Glossary

- **Grading Pipeline**: The asynchronous background task (Pipeline 3) that evaluates a completed interview transcript and produces a scored assessment.
- **Transcript**: The ordered array of `TranscriptTurn` objects (speaker, text, created_at) stored in `practice_sessions.transcript` after a session ends.
- **Dimension Score**: A 0–100 integer score assigned by the LLM to one of four evaluation dimensions: Technical Familiarity, Role Alignment, Communication Skills, and Presence & Engagement.
- **Weighted Raw Score**: The sum of each dimension score multiplied by its assigned weight.
- **Completion Ratio**: The ratio of candidate-answered questions to the expected total of 8 questions, capped at 1.0.
- **Final Overall Score**: The Weighted Raw Score multiplied by the Completion Ratio, rounded to the nearest integer.
- **Practice Verdict**: A human-readable label derived from the Final Overall Score threshold mapping.
- **Technical Round Probes**: An array of 3 deep-dive engineering topics generated by the LLM, tailored to what the candidate discussed in the transcript.
- **InterviewAssessmentSchema**: The Pydantic v2 model defined in `schemas/assessment.py` that validates the full assessment payload before database persistence.
- **interview_assessment**: The JSONB column in `practice_sessions` where the validated assessment payload is stored.
- **OpenRouter**: The LLM gateway used to call high-tier models (Claude 3.5 Sonnet or GPT-4o).
- **Pipeline 3**: The third and final background processing pipeline, triggered by the Phase 9 webhook.
- **Expected Questions**: The fixed count of 8 questions generated per session in Phase 4.
- **Candidate Turn**: A `TranscriptTurn` entry where `speaker == "candidate"`.

## Requirements

### Requirement 1

**User Story:** As a candidate, I want my interview performance to be automatically evaluated after the session ends, so that I receive a detailed report card without any manual intervention.

#### Acceptance Criteria

1. WHEN the Phase 9 webhook transitions a session to `interview_processing`, THE Grading Pipeline SHALL be enqueued as a FastAPI `BackgroundTask` using the existing `grade_session_background` stub in `services/background_pipeline.py`.
2. WHEN the Grading Pipeline starts execution, THE Grading Pipeline SHALL fetch the session's `transcript`, `resume_parsed`, and the associated `practice_jobs.description` (jd_text) from the database using the session_id.
3. IF the session record is not found or `transcript` is null during pipeline execution, THEN THE Grading Pipeline SHALL log the error and terminate without raising an unhandled exception.
4. WHILE the Grading Pipeline is executing, THE system SHALL maintain the session status as `interview_processing` until the assessment is successfully persisted.

---

### Requirement 2

**User Story:** As a candidate, I want my score to reflect how many questions I actually answered, so that incomplete sessions are penalized fairly.

#### Acceptance Criteria

1. THE Grading Pipeline SHALL count the number of distinct Candidate Turns in the transcript where the candidate provided a substantive response, treating this count as the Questions Answered value.
2. THE Grading Pipeline SHALL compute the Completion Ratio as `min(questions_answered / 8, 1.0)`, where 8 is the Expected Questions count.
3. THE Grading Pipeline SHALL compute the Weighted Raw Score as the sum of `(dimension_score * weight)` across all four dimensions using weights: Technical Familiarity 0.50, Role Alignment 0.20, Communication Skills 0.20, Presence & Engagement 0.10.
4. THE Grading Pipeline SHALL compute the Final Overall Score as `round(Weighted Raw Score * Completion Ratio)`, clamped to the range 0–100.
5. WHEN a session contains 4 answered questions out of 8 expected, THE Grading Pipeline SHALL apply a Completion Ratio of 0.5, reducing the Final Overall Score to 50% of the Weighted Raw Score.

---

### Requirement 3

**User Story:** As a candidate, I want the LLM to evaluate my transcript across four specific dimensions, so that I receive targeted feedback on each aspect of my performance.

#### Acceptance Criteria

1. THE Grading Pipeline SHALL instruct the LLM to score the candidate across exactly four dimensions: Technical Familiarity (weight 0.50), Role Alignment (weight 0.20), Communication Skills (weight 0.20), and Presence & Engagement (weight 0.10).
2. THE Grading Pipeline SHALL provide the LLM with the raw `jd_text`, the `resume_parsed` JSON, and the complete `transcript` array as evaluation context.
3. WHEN scoring Technical Familiarity, THE LLM prompt SHALL instruct the evaluator to adjust strictness based on the experience level parsed from the resume, and SHALL prohibit flagging skills or tools not discussed during the conversation as alignment gaps.
4. THE Grading Pipeline SHALL request the LLM to return a structured JSON payload conforming to the `InterviewAssessmentSchema`, including per-dimension `score`, `label`, `verdict`, `evidence`, `strengths`, and `gaps` fields.
5. IF the LLM response cannot be parsed or validated against `InterviewAssessmentSchema`, THEN THE Grading Pipeline SHALL log the validation error and terminate without corrupting the database record.

---

### Requirement 4

**User Story:** As a candidate, I want to receive a clear, supportive verdict label alongside my score, so that I understand where I stand and what to do next.

#### Acceptance Criteria

1. WHEN the Final Overall Score is 80 or above, THE Grading Pipeline SHALL assign the Practice Verdict `"High Alignment"`.
2. WHEN the Final Overall Score is between 68 and 79 inclusive, THE Grading Pipeline SHALL assign the Practice Verdict `"Strong Alignment"`.
3. WHEN the Final Overall Score is between 52 and 67 inclusive, THE Grading Pipeline SHALL assign the Practice Verdict `"Moderate Alignment"`.
4. WHEN the Final Overall Score is below 52, THE Grading Pipeline SHALL assign the Practice Verdict `"Emerging Alignment"`.

---

### Requirement 5

**User Story:** As a candidate, I want to receive 3 personalized technical probe questions after my interview, so that I can prepare for the deep-dive engineering round with a real interviewer.

#### Acceptance Criteria

1. THE Grading Pipeline SHALL instruct the LLM to generate exactly 3 Technical Round Probes as a JSON array of strings.
2. WHEN generating Technical Round Probes, THE LLM prompt SHALL restrict probe topics strictly to subjects the candidate discussed in the transcript, prohibiting generic or off-topic engineering questions.
3. THE Grading Pipeline SHALL include the `technical_round_probes` array in the persisted `InterviewAssessmentSchema` payload.

---

### Requirement 6

**User Story:** As a candidate, I want my assessment to be saved to the database and my session marked as completed, so that the dashboard can display my final report card.

#### Acceptance Criteria

1. WHEN the LLM response is successfully validated against `InterviewAssessmentSchema`, THE Grading Pipeline SHALL write the assessment JSON to `practice_sessions.interview_assessment` and set `status = 'completed'` in a single atomic database update.
2. WHEN a session status is `completed`, THE existing `GET /practice/session/{session_id}` endpoint SHALL expose the `interview_assessment` field in its response without errors.
3. IF the database write fails during assessment persistence, THEN THE Grading Pipeline SHALL log the error and leave the session in `interview_processing` status without retrying.

---

### Requirement 7

**User Story:** As a developer, I want the grading pipeline to use a high-tier LLM model, so that the evaluation quality is consistent with the complexity of the task.

#### Acceptance Criteria

1. THE Grading Pipeline SHALL invoke the LLM via the existing `call_openrouter` function in `api/llm_client.py`.
2. THE Grading Pipeline SHALL use a model identifier configurable via `config.py` settings, defaulting to a high-tier reasoning model (such as `anthropic/claude-3.5-sonnet` or `openai/gpt-4o`).
3. WHILE calling the LLM, THE Grading Pipeline SHALL pass the system prompt and user content as separate message roles, with `response_format` set to `json_object`.
